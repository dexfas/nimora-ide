## Source-level failure mechanism and bounded patch

Existing WebMCP inventory was sequential: it probed each shared page up to 12 seconds within one 20-second total discovery budget. Consequently, three slow yet otherwise shared pages may exhaust discovery time before all three are observed, after which onboarding retries up to 12 times without a meaningful per-page UI message. This is a demonstrated timing-design risk, **not definitive attribution of the Human's live stall**. A third tab that fails to expose a ready composer or is not shared would also prevent the three-healthy-candidate gate.

- WebMCP read-only discovery now explicitly opts into `concurrency: 3` in `extension.js`, with a bounded parallel observation branch in `bounded-browser-tool.js`. It preserves deterministic result order, the same total/per-page deadlines, and fail-closed handling of ambiguous observations; the existing default for other consumers remains sequential. No Worker creation, tool execution, page mutation, extra browser sharing or replay is introduced by discovery concurrency.
- Nimora onboarding source now reports observed/healthy candidate counts, discovery attempts, and phases to the original ShunCode output plus the native progress UI; it bounds overall preparation and refrains from opening *another* page when it sees an existing but degraded shared candidate or when inventory discovery errors. Those changes were verified against the concurrent current source, including a mock test for three already-open pages where only one is initially healthy.
- Tests verified: `npm run test-shuncode-webmcp-bounded-discovery`, `npm run test-shuncode-webmcp-worker-candidates`, `npm run test-shuncode-nimora-web-ai-assembly`, `npm run typecheck-shuncode`, `node --check` for both changed browser bridge JS files, and extension-only bundle rebuild.
