## 原计划需要修正的部分

1. **缺少混合自治产品接线这个主工作项。** 当前扩展的 `ensureAssigned` 要先准备 DeepSeek 页面，再限制 exact candidate；仅给 assignment 增加评分字段不会改变这个流程。新策略必须穿透 Formation、当前 root/Coordinator、Practice 分配、并行 readiness、succession、later-root、完成审核和 Product Shell。
2. **reasoning 不是模型质量。** 当前字段描述事件/传输能力，不能用 reasoning=true 代表“会推理”或“质量高”。语义任务要求、经验证的模型适用性与传输 hard requirements 分开；R5 已有要求不支持的 reasoning 事件导致预拒绝的实测。
3. **先验证一个真实 API，再扩多 Profile。** 单配置真实执行与结果投递先成立，随后两 Profile 同时绑定不同 Mission；避免同时排查协议、凭据、资源身份和调度四层变化。
4. **经济观测不能凭模型名称猜。** Web 不自动等于零成本/有额度；质量无评测就是未知；配额、价格、延迟要有来源/时间/适用范围。未知不记作 0，也不默认更便宜。策略先基于明确允许资源和用户偏好，后接经核实的指标。
5. **budget 与 observations 的权限不同。** 用户允许的付费范围、预算和 Provider 禁止项是治理约束，须版本化持久化并在发送前重核。采样延迟/健康只是观察，不能授予预算或工具权限。选择理由、策略版本和观测依据应可追查；无需把原始网页聊天当真值。
6. **不要另造调度 owner。** 排序在既有 assignment 流程内完成；候选 DTO 目前严格拒绝未知字段，不能随意追加 economics/performance 对象。先明确 typed observation/评分边界，保留刷新、身份核对、Mission lane、资源独占及持久化失败停止。
7. **负向验收不能要求始终零 UNKNOWN。** 顺利路径应零 UNKNOWN/未决投递；故意制造回执丢失时，正确结果可能是 UNKNOWN、停止且零重放。已授权、已执行或结果不明后不得以 fallback 为由再执行一次。
8. **UI 与阻塞准备应提前。** 页面授权、账号未登录、模型不可用和付费同意采用明确 needs-human；默认界面只展示需要完成的动作，保留可选诊断。Native 账号准备和 Stable 合格主机准备不必阻塞其它可验证工作。

## V1 的实现边界

- Goal：让已有混合候选池进入普通自治产品路径，用户提供目标和资源偏好即可工作。
- Owned modules：`extensions/shuncode/src/nimora-autonomy-entry.ts`、`nimora-web-cognition.ts`、`extension.ts`、API/AgentHost candidate sources、Product Shell；domain 的 `worker-assignment.ts`、Mission policy/计划/接班合同按需要最小扩展。Core 默认不新增业务逻辑。
- 保留 ProjectStore、TaskRuntime、MissionCollaborationStore、WorkerSessionManager、assignment、parallel readiness 和 succession owners；资源策略不持有另一套 Mission/Worker 生命周期。
- 初版默认 DeepSeek Cognition；Worker 可选已接入且健康的 Web/API，资源偏好和付费授权明确。缺资源返回 needs-human 或已说明的等待状态，不无限开页/轮询，不静默跨付费边界。
- 排序先过滤 workspace trust、scope、权限/预算、hard requirements、当前健康和资源占用，再按用户 provider/model 偏好与可证明指标排序；发送前刷新。允许在尚未创建/发送且已明确无副作用时选择另一个可用候选，之后依赖既有恢复/接班规则。
- Profile 使用稳定 profileId、非秘密配置版本、真实 backend/provider 与 model 身份；profileId、adapter id、candidateId、sessionId 分开。每会话冻结配置。API key 只由 SecretStorage/ephemeral options 提供，不写 prompts/journals/diagnostics/导出；日志也不公开可识别的凭据指纹。
- capability 向量逐 profile/protocol 证明，不把 adapter 的总能力复制给所有模型。`capabilityRequests=true` 不代表每个工具/路由/参数都获得执行授权。
- “成本优先”先做软选择。硬预算需预留、结算与未知 usage/账单规则、并发预算原子性；未实现前不宣传严格金额上限或自动免费 fallback。无可靠观测的质量/延迟选项不伪装为已验证优化。
- UI 初版同步简化：目标、当前已支持的总文、资源偏好、付费范围；Mission 显示谁处理、选择依据、状态和具体 Human 动作。登录/网站验证/逐页分享/Skills trust/正式完成等原生授权保留，不能承诺用户完全无需连接授权。

## 验证与发布规则

每个阶段分别记录 **Source / Regression / Packaged / Live**，还要记录包 hash、场景、Provider/协议、run/Project/root/input 身份、工具范围、预期与实际结果、证据路径、阻塞原因。Packaged 分为“文件随包且 hash 匹配”与“该分支在包内实际运行”，不能混写。R9 的领域 live PASS 不自动覆盖 R10 新 UI/cleanup 分支。

R10 正向 toast 用实际非 modal 通知/真实页面观测；modal 取消应零发送。archive 只操作本次可丢弃且已退休、已收敛的确切会话，保留 Human 确认和原对话记录，不 fallback delete；无法证明结果则保留 UNKNOWN/no-replay，不改为 PASS。顺利路径零 UNKNOWN，负向路径验证准确拒绝/记录。

回归以修改范围为准：第一方 typecheck/build/runtime、assignment/候选漂移、实际 domain→adapter→executor→receipt 合同；混合自治增加公开产品命令/真实 Webview、单 current Worker、并发资源竞争与 scope 隔离验证。每个后端用新身份执行一次有界真实请求，真实凭据不进入聊天或证据。

故障按步骤注入：格式错误、限流、关闭空闲页、已知 settled 容量接班、延迟 delivery，再测试重启与组合。运行中/未决副作用不按已知 settled 处理；故障后的“需要 Human”可作为正确退出。先确认资源和文件权限隔离，再扩大并发数量。

RC manifest 必须列出 source/package hash、支持且 live 验证的通道、仍 gated 的通道、证据和 Stable gate。RC 支持范围若调整则明示，不将受阻 AgentHost 或未经现场验证的接口列为默认支持；“唯一 current Beta”指发行 manifest 当前指针，历史包与 proof 保留。该指针只有达到已声明门槛后更新。

回滚禁用新增入口/策略/profile source 并正常重建；保留旧 DeepSeek 支持路径、canonical journals、grants、completion scopes 与已消费输入。不得清空 latch 或重发旧请求以验证回滚。
