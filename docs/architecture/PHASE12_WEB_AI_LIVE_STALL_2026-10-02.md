## Diagnosed design gap; fixes staged on disk, not yet live-accepted

- In the originally inspected resource-discovery code, three page observations could run serially under a single `20s` total deadline, although each page probe was independently allowed `12s`. Repeated outer polling could make the progress notification appear stuck for many minutes. Concurrent independent read-only discovery (maximum three) is present in the updated `bounded-browser-tool.js`/bridge source, but **the exact cause of this specific live stall is unproven** until a fresh runtime produces candidate readiness diagnostics. A slow/degraded third page or incomplete sharing are also possible.
- `nimora-web-ai-onboarding.ts` now has a bounded automated-discovery interval (default two minutes; time spent in an explicitly user-controlled native page-opening/login/share-consent step is excluded), explicit `healthy/required` and `observed` counts, diagnostic discovery errors, and a fail-closed rule preventing a fourth tab when three shared-but-degraded candidate pages already exist. If initial discovery fails, it does **not** infer an empty tab inventory or open duplicates. It never sends a Mission merely to probe resource readiness.
- The product progress notification now reports the observed resource count and remaining check attempts; the extension writes bounded, non-content preparation status to its output channel. The WebMCP bridge now logs only short page identifier prefixes and minimal readiness flags (provider, composer/auth/compatibility/ready), never message text, cookies or full URLs. On deadline, the user receives an explicit failure report rather than another indefinite retry loop.
- Fresh isolated regression tests cover three already shared pages with initially degraded composers, refusing to open duplicates on unreadable discovery, a persistent 1/3 degraded observation, and expiry of the overall deadline. These do not stand in for live sharing or provider execution.
